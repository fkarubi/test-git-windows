# ホームセンター 店内サポートアプリ 企画プラン

お客様の2大困りごと ——「**商品の使い方が分からない**」「**どこにあるのか分からない**」——
を解決するアプリの企画・開発プランです。

---

## 1. 課題の再定義

2つの困りごとは、別々の問題に見えて根は同じです。

> **店員に聞かないと分からない。しかし店員はいつも捕まらない。**

つまりこのアプリの本質は「新しい便利機能」ではなく、
**店員の知識と店内の地図を、お客様の手元に置くこと**です。

さらに、現場を想像すると **2つの困りごとの手前にもう1段ある**ことに気づきます。
ホームセンターは「目的買い」の店だからです。

| 層 | お客様の頭の中 | 例 |
|---|---|---|
| ① 商品選定 | やりたいことは決まっているが、何を買えばいいか分からない | 「壁に棚を付けたい」 |
| ② 場所 | 買う物は決まったが、どこにあるか分からない | 「アンカーはどこ？」 |
| ③ 使い方 | 買ったが、使い方が分からない | 「下地が石膏ボードでも大丈夫？」 |

**①→②→③ を1本の流れでつなぐ**のが、このアプリの差別化ポイントです。
単体の商品検索アプリや売場マップは既に世の中にありますが、
「目的 → 必要な材料一式 → 売場ルート → 使い方」を通しで案内するものはほぼありません。

---

## 2. ターゲットユーザー

| 優先 | ユーザー | ニーズ |
|---|---|---|
| **主** | ライトDIY層（来店頻度は月1回未満） | 何を買えばいいか分からない。一番困っていて、一番店員に聞く層 |
| 副 | プロ職人・常連 | 場所だけ最短で知りたい。スピード重視 |
| **隠れた第2の主役** | 店員（特に新人・応援スタッフ） | 同じアプリで即答できる。売場異動しても戦力になる |

> 店員を「置き換える」のではなく「助ける」道具として設計します。
> 店員が現場で使ってくれることが、データ更新が回り続ける条件でもあります。

---

## 3. 機能案

### ② 場所を解決する

- **商品検索 → 売場番号 + フロアマップ上にピン表示**
- 案内粒度は「**通路A-12 / 右手・棚3段目**」で十分。
- 買い物リストの**取得順を店内動線で最適化**（レジまで一筆書き）
- 「棚に無かった」報告ボタン（→ データ更新のトリガーになる）

> **屋内測位（BLEビーコン・AR ナビ）は初期にはやりません。**
> 設置・保守コストが高いわりに、「通路番号が分かれば人は辿り着ける」ため費用対効果が合いません。

### ③ 使い方を解決する

- **バーコード / 商品写真をスキャン** → 使い方・注意点・必要な付属品を表示
- 施工手順、下地・サイズなどの選び方、よくある失敗
- メーカー取説 PDF・施工動画へのリンク
- 「この商品を使うには他に何が要る？」（例: ビス、下地探し、電動ドライバー）

### ① 商品選定を解決する（差別化の核）

- **やりたいことを話しかけると、必要な材料一式をリスト化**
  例:「石膏ボードの壁に幅60cmの棚を付けたい」
  → 棚受け / ボードアンカー / ビス / 下地センサー を提案 → それぞれの売場を地図に表示
- そのまま買い物リスト化 → ルート案内へ

### 安全設計（必須要件）

以下は **AIに答えさせず、有人・有資格者へ誘導**します。

- 電気工事、ガス、給排水の本設工事
- 高所作業、電動工具の危険な使い方
- 農薬・塗料・溶剤などの化学品の取り扱い

すべての回答に**出典（メーカー取説へのリンク）**を表示し、
「最終判断は取扱説明書に従ってください」の注記を必ず添えます。

## 4. MVPスコープ

### 作るもの

- **PWA（Webアプリ）** — アプリDL不要。店内POP・カートのQRから起動
- 商品検索 + 売場位置表示（静止フロアマップ + 通路/棚番号）
- AIチャット（目的 → 商品提案 → 場所 → 使い方）
- バーコードスキャン
- **店員用の管理画面**（売場位置とFAQをその場で修正できる）
- **対象は1店舗・1フロア・2〜3カテゴリのみ**（例: DIY資材／水回り）

### 初期は作らないもの

ネイティブアプリ / 屋内ナビ / リアルタイム在庫連携 / 会員・決済連携 /
多言語 / 全カテゴリ対応 / レビュー・コミュニティ機能

> 最初から全店・全カテゴリを狙うと、後述のデータ整備で必ず頓挫します。

---

## 5. 最大の難所は「技術」ではなく「データ」

実装難易度自体は高くありません。**勝負はデータ整備と、その鮮度を保つ運用**です。

| 必要なデータ | 入手元 | 難易度 |
|---|---|---|
| 商品マスタ（JAN・名称・価格・カテゴリ） | 既存POS / EC サイト | 低 |
| **売場位置（通路・棚番号）** | 棚割データがあれば流用、無ければ手作業 | **高** |
| 使い方情報 | メーカー取説PDF・社内FAQ・店員の暗黙知 | 中 |

### 売場位置データの現実解

- 数万SKU 全部に座標を振るのは**非現実的**。
- → **「商品カテゴリ × 売場」の粒度で紐付ける。**
  数百件のマッピングで実用上9割をカバーできます。
- → 需要の高い主力商品だけ、後から個別に棚番号を精緻化。

### 鮮度を保つ仕組み（最重要）

売場位置は**棚替えで必ず陳腐化します**。ここを後回しにすると、半年でアプリは信用を失います。

- 店員が**現場から2タップで位置を直せる**管理画面を **MVP に含める**
- お客様の「棚に無かった」報告を店員のタスクに流す
- 棚替え時の更新を店舗オペレーションに組み込む（作業手順書に1行足す）

### 使い方情報

- メーカー取説PDF を取り込み、**RAG（検索拡張生成）**で回答
- **店員が「よく聞かれる質問」を100件書き出す**
  → これが最初のFAQ になり、同時に**AIの精度を測る評価データセット**になります

## 6. 技術構成（案）

| 領域 | 選択 | 理由 |
|---|---|---|
| フロント | Next.js + TypeScript（PWA） | DL不要でQRから即起動。iOS/Android両対応が1コードで済む |
| バックエンド | Node（API Routes） | フロントと同一言語で小さく回せる |
| DB | PostgreSQL + pgvector | 商品マスタとベクトル検索を1つのDBで完結 |
| 検索 | 全文検索 + ベクトル検索のハイブリッド | 型番の完全一致と曖昧な言い回しの両方に対応 |
| AI | Claude API（主: `claude-sonnet-5`／難問: `claude-opus-5`） | 会話での要件ヒアリングと材料一式の提案に強い |
| バーコード | ブラウザ標準 `BarcodeDetector`（フォールバック: ZXing） | 追加SDK不要 |
| 地図 | SVG フロアマップにピン | 初期は既存の店内マップ画像で十分 |
| インフラ | Vercel + マネージドPostgres | 運用要員を持たずに始められる |

## 7. 進め方（フェーズ）

### Phase 0: 課題検証（2週間）— **コードを書かない**

いきなり作らず、まず前提が正しいかを確かめます。

1. 店舗で半日観察し、店員に同行する
2. **実際に聞かれた質問を100件収集**してスプレッドシート化
3. よくある質問トップ20を特定する
4. 既存データ（商品マスタ・棚割）の有無と形式を棚卸しする
5. **Wizard of Oz テスト**を1日実施
   タブレットやLINEで受付だけ用意し、裏側は人間が回答する。
   「本当に使われるか」「お客様はどんな言葉で聞いてくるか」を、作る前に確かめます。
6. ベースラインを計測（店員を捕まえるまでの平均待ち時間、諦めて帰る率）

> **ここでニーズが薄ければ作りません。** この2週間が一番コスパの高い投資です。

### Phase 1: MVP開発（4〜6週間）— 1店舗・限定カテゴリ

- 上記MVPスコープを実装
- Phase 0 の質問100件を評価セットにして回答精度を測定
- 店員向け管理画面を同時にリリース

### Phase 2: 店内実証（4週間）

- 店内POP・カート・サイネージにQRを設置
- 利用ログ分析、**答えられなかった質問**を毎週レビューして改善
- 店員モードの機能拡充

### Phase 3: 拡大

- 全カテゴリ・多店舗展開、在庫連携、多言語（インバウンド/技能実習生）、動画コンテンツ

## 8. 成功指標（KPI）

| 区分 | 指標 |
|---|---|
| **主要** | 商品への到達率（案内後に「見つかった」と回答した割合） |
| **主要** | 回答満足度（👍/👎） |
| 副次 | 店員への同種質問の減少（店員アンケートで測定） |
| 副次 | 目的買いの完了率（提案リストのうち購入に至った割合） |
| 事業 | 客単価、関連商品の同時購入率、再利用率 |

Phase 0 で現状値（ベースライン）を取っておくことが前提です。

---

## 9. リスクと対策

| リスク | 対策 |
|---|---|
| **位置データが棚替えですぐ古くなる** | 店員が現場から直せるUI／お客様の「無かった」報告／棚替え手順に更新を組み込む |
| **AIが誤った使い方を答え、事故につながる** | 危険カテゴリは有人誘導、出典リンク必須、免責表示、回答ログの人間レビュー |
| 誰も使わない（アプリDLの壁） | PWA + 店内QR。インストール不要にする |
| 店内の電波が弱い | 店舗Wi-Fi整備、軽量化、主要データのオフラインキャッシュ |
| 店員の抵抗（仕事を奪われる懸念） | 「店員を助ける道具」として設計し、店員モードを同時提供 |
| 商品情報の著作権（メーカー取説） | 全文転載せず要約+出典リンク。必要に応じてメーカーへ利用許諾を確認 |

---

## 10. 最初の2週間でやること

1. 対象店舗を1つ、対象カテゴリを2〜3つ決める
2. 店舗で半日観察 + 店員3名にインタビュー
3. お客様からの質問を100件収集してスプレッドシート化
4. 商品マスタ・棚割データの有無と形式を確認する
5. Wizard of Oz テストを1日実施し、作る価値があるか判断する

---

## 補足: このプランの考え方

- **技術的な難所はほとんどありません。** 難所はデータ整備と、その鮮度を保つ運用です。
  だからこそ「店員が直せる管理画面」を MVP から外しません。
- **範囲を絞ることが成功条件です。** 1店舗・数カテゴリで完成度を出し、
  「使える」と現場に認めさせてから広げます。
- **Phase 0 を飛ばさないでください。** 作ってから「誰も使わなかった」が一番高くつきます。
