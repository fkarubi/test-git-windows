# ホームセンター 店内サポートアプリ 企画プラン

お客様の2大困りごと ——「**商品の使い方が分からない**」「**どこにあるのか分からない**」——
を解決するアプリの企画・開発プランです。

---

## 1. 課題の再定義

2つの困りごとは、別々の問題に見えて根は同じです。

> **店員に聞かないと分からない。しかし店員はいつも捕まらない。**

つまりこのアプリの本質は「新しい便利機能」ではなく、
**店員の知識と店内の地図を、お客様の手元に置くこと**です。

さらに、現場を想像すると **2つの困りごとの手前にもう1段ある**ことに気づきます。
ホームセンターは「目的買い」の店だからです。

| 層 | お客様の頭の中 | 例 |
|---|---|---|
| ① 商品選定 | やりたいことは決まっているが、何を買えばいいか分からない | 「壁に棚を付けたい」 |
| ② 場所 | 買う物は決まったが、どこにあるか分からない | 「アンカーはどこ？」 |
| ③ 使い方 | 買ったが、使い方が分からない | 「下地が石膏ボードでも大丈夫？」 |

**①→②→③ を1本の流れでつなぐ**のが、このアプリの差別化ポイントです。
単体の商品検索アプリや売場マップは既に世の中にありますが、
「目的 → 必要な材料一式 → 売場ルート → 使い方」を通しで案内するものはほぼありません。

## 2. ターゲットユーザー

| 優先 | ユーザー | ニーズ |
|---|---|---|
| **最初の主役** | 店員（特に新人・応援スタッフ） | 接客中に即答したい。売場異動しても戦力になりたい |
| 本命 | ライトDIY層（来店頻度は月1回未満） | 何を買えばいいか分からない。一番困っていて、一番店員に聞く層 |
| 副 | プロ職人・常連 | 場所だけ最短で知りたい。スピード重視 |

最終的な本命はライトDIY層ですが、**最初に届けるべきは店員**です。理由は次章に書きます。

## 3. 店員に使ってもらうための設計

### 3.1 なぜ「店員向けを先に出す」べきか

同じ中身のアプリでも、店員向けに先に出す方が立ち上がりが速く、リスクも小さくなります。

| | 店員向け | お客様向け |
|---|---|---|
| ユーザー数 | 1店舗で数十人 | 1日数百〜数千人 |
| 教育 | できる（朝礼・研修） | できない |
| **誤答リスク** | **店員が最終フィルターになる** | 直接お客様に届く |
| フィードバック | 名前と顔が分かる。その場で聞ける | 匿名のログのみ |
| **データ整備** | **使う人が、直せる人** | 直せない |

とくに3行目が決定的です。AIが誤った使い方を答えても、店員が「いや、それは違う」と気づいて止められます。
お客様向けを先に出すと、この安全弁がありません。

そして5行目。**売場位置データの鮮度**という最大の難所は、
店員が日常的にアプリを使っているときにしか解けません。
「使う」と「直す」が同じ人の同じ行動の中にある状態を、先に作ります。

> **提案: Phase 1 を「店員向け先行リリース」に変更します。**
> お客様向けの公開は、知識と位置データが育ったあとの Phase 3 に置きます。

### 3.2 接客中に立ちはだかる3つの壁

機能の良し悪し以前に、現場には3つの壁があります。ここを外すと、どんなに賢くても使われません。

#### 壁1 — 接客中に使えるのは「5秒」

- 起動 → 検索 → 答え が**3タップ以内**。それ以上かかるなら「無線で先輩に聞く」方が速い
- 起動直後に**いきなり検索窓**を出す。ホーム画面もメニューもいらない
- **ログインは店舗単位で維持**。毎回ログインさせたら、それだけで使われなくなります
- 音声入力と片手操作（もう片方の手は商品を持っています）

#### 壁2 — お客様の前で端末を触りにくい

「接客中にスマホをいじっている」と見られるのを、現場は最も嫌がります。

- 対策は隠すことではなく、**お客様に見せる前提のUIにする**こと
- 大きな商品画像、図解、手順のイラスト。店員が読み上げるのではなく、**画面を一緒に覗き込む**形にする
- そうすれば端末は「サボり」ではなく「カタログ」になり、抵抗が消えます

#### 壁3 — 答えが分かっても、言い方が分からない

新人が本当に困るのは、知識よりも**どう説明するか**です。

- 回答に**接客トークの例文**を添える（「この場合は〜とお伝えすると伝わりやすいです」）
- **先に確認すべきこと**を出す（「壁の下地は何ですか？」「何kg載せますか？」）
- これは新人の一人立ちを直接早めます

### 3.3 「分からない」を価値に変える

AIが答えられない質問は必ず出ます。**ここでアプリが無力に見えると、二度と使われません。**

- **「詳しい者を呼ぶ」ボタン** — その商品カテゴリの担当者名と内線／インカム番号を表示
- **「これ聞かれた」1タップ記録** — 答えられなかった質問が未回答リストに溜まる
- 未回答リストは、そのまま次の改善バックログになります

### 3.4 知識が育つ仕組み（ここが本体）

このアプリの本当の価値は、**ベテランの暗黙知が店舗の資産になる**ことです。

1. 店員が「これ聞かれた」を記録する（5秒）
2. ベテランが空き時間に回答を書く（音声で吹き込んで文字起こしでも可）
3. AIが次からその回答を使う
4. **「あなたの回答が今週23回使われました」**と、書いた本人に返す

**4番が肝です。** ベテランは「自分の知識が要らなくなる」と警戒します。
逆に**監修者としてクレジットする**設計にすれば、承認欲求を満たす側に回ります。
売場位置の修正も同じで、2タップで直せて、直したことが本人に見える形にします。

### 3.5 導入の進め方（機能より、ここで決まる）

現場は「また本部が変なものを入れてきた」と身構えます。ツールの出来より導入設計で決まります。

1. **アーリーアダプターを3人選ぶ** — 新人だけでなく、**ベテランを必ず1人入れる**。
   ベテランが使っていれば全体に広がります
2. **朝礼で1分のデモ** — 資料は配らない。実際に1問聞いてみせる
3. **最初の2週間は「聞かれた質問を記録するだけ」でいい** — いきなり全機能を使わせない
4. **業務時間内に組み込む** — 「空き時間にやっといて」で回るものはありません
5. **週1回5分、未回答リストを全員で見る** — 自分の記録が反映されるのが見えると続きます

### 3.6 絶対にやってはいけないこと

> **個人単位の利用ログを人事評価に使わない。そして、使わないと明言する。**

「誰が何回アプリを使ったか」を評価に持ち込んだ瞬間、このアプリは監視ツールになり、
現場は使うのをやめます（あるいは、意味のない操作で数字だけ作ります）。
集計は**店舗単位・売場単位まで**にとどめ、導入時にそれを口頭で伝えてください。

### 3.7 店員向けMVPに入れるもの

- 起動直後の検索窓（商品名・型番・曖昧な言い回しに対応）
- 商品位置（通路・棚番号）+ **2タップで位置を修正**
- 使い方回答 + **出典リンク** + **接客トーク例文** + **先に確認すべきこと**
- **「これ聞かれた」1タップ記録**
- **「詳しい者を呼ぶ」** — 担当者と連絡先
- 店舗単位のログイン維持、音声入力

### 3.8 店員向けの測り方

| 指標 | 見るもの |
|---|---|
| **週次利用率**（利用店員数 ÷ 在籍店員数） | **定着したかどうか。最重要** |
| 新人が一人で接客できるまでの日数 | 教育コストへの効果 |
| 「先輩を呼ぶ」回数 | 接客の自己完結率 |
| 未回答質問の解消率 | 知識が育っているか |
| 位置修正の件数 | データの鮮度が保たれているか |

利用率が2週目に落ちたら、機能ではなく **壁1（速さ）か導入設計**を疑ってください。

## 4. 機能案

### ② 場所を解決する

- **商品検索 → 売場番号 + フロアマップ上にピン表示**
- 案内粒度は「**通路A-12 / 右手・棚3段目**」で十分。
- 買い物リストの**取得順を店内動線で最適化**（レジまで一筆書き）
- 「棚に無かった」報告ボタン（→ データ更新のトリガーになる）

> **屋内測位（BLEビーコン・AR ナビ）は初期にはやりません。**
> 設置・保守コストが高いわりに、「通路番号が分かれば人は辿り着ける」ため費用対効果が合いません。

### ③ 使い方を解決する

- **バーコード / 商品写真をスキャン** → 使い方・注意点・必要な付属品を表示
- 施工手順、下地・サイズなどの選び方、よくある失敗
- メーカー取説 PDF・施工動画へのリンク
- 「この商品を使うには他に何が要る？」（例: ビス、下地探し、電動ドライバー）

### ① 商品選定を解決する（差別化の核）

- **やりたいことを話しかけると、必要な材料一式をリスト化**
  例:「石膏ボードの壁に幅60cmの棚を付けたい」
  → 棚受け / ボードアンカー / ビス / 下地センサー を提案 → それぞれの売場を地図に表示
- そのまま買い物リスト化 → ルート案内へ

### 安全設計（必須要件）

以下は **AIに答えさせず、有人・有資格者へ誘導**します。

- 電気工事、ガス、給排水の本設工事
- 高所作業、電動工具の危険な使い方
- 農薬・塗料・溶剤などの化学品の取り扱い

すべての回答に**出典（メーカー取説へのリンク）**を表示し、
「最終判断は取扱説明書に従ってください」の注記を必ず添えます。

## 5. MVPスコープ

### 作るもの

- **PWA（Webアプリ）** — アプリDL不要。店員は端末のホームに追加、お客様は店内QRから起動
- **店員モードを先に完成させる**（3.7 の機能一式）
- 商品検索 + 売場位置表示（静止フロアマップ + 通路/棚番号）
- AIチャット（目的 → 商品提案 → 場所 → 使い方）
- バーコードスキャン
- **売場位置とFAQをその場で修正できる編集機能**
- **対象は1店舗・1フロア・2〜3カテゴリのみ**（例: DIY資材／水回り）

### 初期は作らないもの

ネイティブアプリ / 屋内ナビ / リアルタイム在庫連携 / 会員・決済連携 /
多言語 / 全カテゴリ対応 / レビュー・コミュニティ機能

> 最初から全店・全カテゴリを狙うと、後述のデータ整備で必ず頓挫します。

## 6. 最大の難所は「技術」ではなく「データ」

実装難易度自体は高くありません。**勝負はデータ整備と、その鮮度を保つ運用**です。

| 必要なデータ | 入手元 | 難易度 |
|---|---|---|
| 商品マスタ（JAN・名称・価格・カテゴリ） | 既存POS / EC サイト | 低 |
| **売場位置（通路・棚番号）** | 棚割データがあれば流用、無ければ手作業 | **高** |
| 使い方情報 | メーカー取説PDF・社内FAQ・店員の暗黙知 | 中 |

### 売場位置データの現実解

- 数万SKU 全部に座標を振るのは**非現実的**。
- → **「商品カテゴリ × 売場」の粒度で紐付ける。**
  数百件のマッピングで実用上9割をカバーできます。
- → 需要の高い主力商品だけ、後から個別に棚番号を精緻化。

### 鮮度を保つ仕組み（最重要）

売場位置は**棚替えで必ず陳腐化します**。ここを後回しにすると、半年でアプリは信用を失います。

- 店員が**現場から2タップで位置を直せる**ようにする（**MVP に含める**）
- お客様の「棚に無かった」報告を店員のタスクに流す
- 棚替え時の更新を店舗オペレーションに組み込む（作業手順書に1行足す）

**店員向け先行リリースは、この仕組みを回すための助走期間でもあります。**

### 使い方情報

- メーカー取説PDF を取り込み、**RAG（検索拡張生成）**で回答
- **店員が「よく聞かれる質問」を100件書き出す**
  → これが最初のFAQ になり、同時に**AIの精度を測る評価データセット**になります

## 7. 技術構成（案）

| 領域 | 選択 | 理由 |
|---|---|---|
| フロント | Next.js + TypeScript（PWA） | DL不要。店員端末とお客様端末で同一コードが使える |
| バックエンド | Node（API Routes） | フロントと同一言語で小さく回せる |
| DB | PostgreSQL + pgvector | 商品マスタとベクトル検索を1つのDBで完結 |
| 検索 | 全文検索 + ベクトル検索のハイブリッド | 型番の完全一致と曖昧な言い回しの両方に対応 |
| AI | Claude API（主: sonnet 系／難問: opus 系） | 会話での要件ヒアリングと材料一式の提案に強い |
| バーコード | ブラウザ標準 `BarcodeDetector`（フォールバック: ZXing） | 追加SDK不要 |
| 地図 | SVG フロアマップにピン | 初期は既存の店内マップ画像で十分 |
| 認証 | 店舗単位のデバイス認証（店員） / 認証なし（お客様） | 接客中のログイン操作をゼロにする |
| インフラ | Vercel + マネージドPostgres | 運用要員を持たずに始められる |

## 8. 進め方（フェーズ）

### Phase 0: 課題検証（2週間）— **コードを書かない**

いきなり作らず、まず前提が正しいかを確かめます。

1. 店舗で半日観察し、店員に同行する
2. **実際に聞かれた質問を100件収集**してスプレッドシート化
3. よくある質問トップ20を特定する
4. 既存データ（商品マスタ・棚割）の有無と形式を棚卸しする
5. **Wizard of Oz テスト**を1日実施
   タブレットやLINEで受付だけ用意し、裏側は人間が回答する。
   「本当に使われるか」「お客様はどんな言葉で聞いてくるか」を、作る前に確かめます。
6. ベースラインを計測（店員を捕まえるまでの平均待ち時間、諦めて帰る率）
7. **アーリーアダプターの店員3名を決める**（ベテランを必ず1人含める）

> **ここでニーズが薄ければ作りません。** この2週間が一番コスパの高い投資です。

### Phase 1: 店員向け先行リリース（4〜6週間）— 1店舗・限定カテゴリ

- 3.7 の店員向けMVPを実装
- Phase 0 の質問100件を評価セットにして回答精度を測定
- **お客様には公開しない。** 店員だけが使う期間にする

### Phase 2: 定着とナレッジ育成（4週間）

- 週次利用率を追う（3.8 の指標）
- **未回答リストをベテランが埋める運用**を回す
- 売場位置の修正が日常業務に入っているかを確認
- 答えられなかった質問を毎週レビューして改善

### Phase 3: お客様向け公開（4週間）

- 知識と位置データが育ったところで、店内POP・カート・サイネージにQRを設置
- 目的からの逆引き（Layer 1）を本格投入
- 利用ログ分析、店員への質問がどう変わったかを測定

### Phase 4: 拡大

- 全カテゴリ・多店舗展開、在庫連携、多言語（インバウンド／技能実習生）、動画コンテンツ

## 9. 成功指標（KPI）

### 店員向け（Phase 1〜2）

| 区分 | 指標 |
|---|---|
| **主要** | 週次利用率（利用店員数 ÷ 在籍店員数） |
| **主要** | 未回答質問の解消率 |
| 副次 | 新人が一人で接客できるまでの日数 |
| 副次 | 位置修正の件数（データ鮮度の代理指標） |

### お客様向け（Phase 3〜）

| 区分 | 指標 |
|---|---|
| **主要** | 商品への到達率（案内後に「見つかった」と回答した割合） |
| **主要** | 回答満足度（👍/👎） |
| 副次 | 店員への同種質問の減少 |
| 副次 | 目的買いの完了率（提案リストのうち購入に至った割合） |
| 事業 | 客単価、関連商品の同時購入率、再利用率 |

Phase 0 で現状値（ベースライン）を取っておくことが前提です。

## 10. リスクと対策

| リスク | 対策 |
|---|---|
| **位置データが棚替えですぐ古くなる** | 店員が現場から直せるUI／お客様の「無かった」報告／棚替え手順に更新を組み込む |
| **AIが誤った使い方を答え、事故につながる** | 危険カテゴリは有人誘導、出典リンク必須、免責表示、回答ログの人間レビュー。**店員向け先行リリースで、店員を最終フィルターにする** |
| **店員に監視ツールと見なされる** | 個人単位の利用ログを評価に使わない。集計は店舗・売場単位まで。導入時に明言する |
| **ベテランの抵抗（知識を奪われる懸念）** | 回答の監修者としてクレジット。「あなたの回答が今週◯回使われました」を返す |
| 接客中に使ってもらえない | 3タップ以内、ログイン維持、音声入力、お客様に見せる前提のUI |
| 誰も使わない（アプリDLの壁） | PWA + 店内QR。インストール不要にする |
| 店内の電波が弱い | 店舗Wi-Fi整備、軽量化、主要データのオフラインキャッシュ |
| 商品情報の著作権（メーカー取説） | 全文転載せず要約+出典リンク。必要に応じてメーカーへ利用許諾を確認 |

## 11. 最初の2週間でやること

1. 対象店舗を1つ、対象カテゴリを2〜3つ決める
2. 店舗で半日観察 + 店員3名にインタビュー
3. お客様からの質問を100件収集してスプレッドシート化
4. 商品マスタ・棚割データの有無と形式を確認する
5. **アーリーアダプターの店員3名を決める**（ベテランを1人含める）
6. Wizard of Oz テストを1日実施し、作る価値があるか判断する

## 補足: このプランの考え方

- **まず店員に届ける。** 店員は最終フィルターであり、データを直せる唯一の人です。
  お客様向けの公開は、知識と位置データが育ってからで遅くありません。
- **技術的な難所はほとんどありません。** 難所はデータ整備と、その鮮度を保つ運用です。
